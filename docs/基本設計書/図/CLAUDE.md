## 設計書の図（PlantUML）

- 図は `docs/基本設計書/図/<図の種類>/` に PlantUML（`.puml`、UTF-8）で書き、同じ名前の `.svg` を同じフォルダに出力する。PNG は使わない。
- 図は仕様書（`docs/基本設計書/仕様書.md`）をもとに描く。コードから直接描かない。機能ID・機能名・日本語の名前は仕様書の機能一覧と名前の対応表に合わせる。
- ファイル名（＝図名）は機能IDで始める。機能の数が変わっても付け直さずに済むよう、機能一覧の No は使わない。
  - ユースケース図: `<グループID>_<システム名>_ユースケース図`（例: `B01_基本設定システム_ユースケース図`）。システム名は仕様書 5.1 の表の1行目（`**B01_基本設定システム**`）の名前。全体の図（`全体_楽曲生成システムToniq_ユースケース図`）は作らない（2026-11-16 決定。ファイルは残っているが更新しない）。仕様書・docx の見出しには「_ユースケース図」を付けない（`B01_基本設定システム`）
  - ロバストネス図・シーケンス図・クラス図: `<機能ID>_<機能名>機能_<図の種類>`（例: `B01-1_BPM選択機能_ロバストネス図`。機能名は仕様書の機能一覧の名前）。クラスの全体図（`全体_クラス図`）は作らない（2026-11-16 決定。ファイルは残っているが更新しない）
- `.puml` を追加・修正したら、対応する `.svg` も作り直す。変換後に `.svg` の中を「Syntax Error」で検索して、エラーが無いことを確かめる。
- 見た目は astah 風にそろえる。`@startuml` の直後で、図の種類ごとの共通設定を `!include` する。図の中に `skinparam` を書かない。
  - ユースケース図: `!include ../astah-usecase-style.puml`、枠は `mainframe **uc** <図名>`
  - ロバストネス図: `!include ../astah-robustness-style.puml`、枠は `mainframe **uc** <図名>`
  - シーケンス図: `!include ../astah-sequence-style.puml`、枠は `mainframe sd <図名>`
  - クラス図: `!include ../astah-class-style.puml`、枠は `mainframe **pkg**`
  - 画面遷移図: `!include ../astah-state-style.puml`、枠は `mainframe **stm** <図名>`
  - システム概要図・システム構成図: `!include ../astah-system-style.puml`、枠は `mainframe **deployment** <図名>`（並べる向き `left to right direction` / `top to bottom direction` は図ごとに書く）
- `title` は使わない（枠に図名を入れる）。
- 共通設定ファイル（`astah-*.puml`）には `@startuml` / `@enduml` を書かない。
- 名前は日本語で書く。画面・処理・データ・クラス・操作・属性に、コードの識別子（`SimpleScreen`、`setState()` など）は使わず、日本語の名詞・動詞にする（例: 「シンプルモード画面」「コード進行を再抽選する()」「コード進行マスタ」）。同じものはどの図でも同じ名前にする。
- 細かさは利用者の操作の単位にそろえる。画面の描き直し・状態の読み書きなど、画面の中の細かい呼び出しは書かない。
- ユースケース図: 利用者は `actor "利用者" as A1`。利用者とユースケースは `A1 -- UC1`（矢印なし）でつなぐ。
  - システム名は境界（システムの範囲の四角）の外側の上に出す。名前だけの外側の四角（ステレオタイプ `<<システム名>>`。枠線なし・共通設定で定義）の中に、名前なしの境界の四角を入れる：
    ```
    rectangle "基本設定システム" <<システム名>> {
      rectangle " " {
        usecase "BPM選択機能" as UC1
      }
    }
    ```
  - グループの図のシステム名は、そのグループのシステム名（仕様書 5.1）。
- ロバストネス図: `actor` / `boundary`（画面）/ `control`（処理）/ `entity`（データ）を使う。線は向きのある矢印 `-->` で書き、線には操作や条件を書く（例: `A1 --> B1 : 生成するボタンを押下する`）。
  - つないでよいのは、利用者 → 画面、画面 → 処理、処理 → 処理、処理 → データ、処理 → 画面（処理の結果として別の画面へ移る・画面に表示する）。利用者 → 処理・データ、画面 → 画面、画面 → データはつながない（間に処理を置く）。
  - 入力が足りないなどで先へ進めないときは、処理の自己ループで書く（例: `C1 --> C1 : ファイルが選択されていない`）。
  - 自己ループは、先へ進めない・取り消される条件と、その処理の中だけで終わる短い動きにだけ使い、1つの処理に1本までにする。合成・変換などの処理の手順は自己ループにせず、別の処理（control）として描く（例: A01-5 の「音声合成」「音声変換」。名前は仕様書の付録A に足し、シーケンス図・クラス図もそろえる）。
  - 自己ループのラベルは横に長いとほかの線のラベルに重なるので、13文字くらいで `\n` で改行する（「（」の前、「、」の後、助詞の後で切る。英単語の途中では切らない）。例: `C1 --> C1 : 未保存の曲を\n捨てる確認で取り消した\n（開かない）`
  - 線の文（ラベル）は、どの矢印の文か分かるよう、その矢印のすぐ上に矢印と平行に置く。PlantUML ではそう置けないので、SVG に変換したあと `node docs/基本設計書/tools/robustness_labels.mjs`（リポジトリのルートで。ロバストネス図のフォルダの SVG をすべて処理し、処理済みの SVG は変えない）で置き直す。スクリプトは線に沿って、ほかの文・線・アイコンと重ならない位置を選び、文を線より手前に白い下地付きで描く（2026-11-12 決定）。
    - 置き直した SVG は手で直さない。文の位置を変えたいときは .puml（ラベルの文・改行）を直して変換し直し、スクリプトをもう一度動かす。
    - スクリプトが「重なり N 件」と出した図は、ラベルを短くする・`\n` で改行するなどして .puml を直す。
    - 自己ループの文は PlantUML の位置（ループの上）のまま。ほかの線に横切られるときだけ、ループの近くで少しずらす。
  - 置き直したら、文字どうし・文字と線が重なっていないか画像で確かめる（Edge か Chrome のヘッドレスで SVG を PNG にして見る。`robustness_labels.mjs <SVG> --png <フォルダ>` で作れる）。
- シーケンス図: 参加者の表示名は先頭に「:」を付ける（`actor ":利用者" as L1`、`boundary ":シンプルモード画面" as L2`）。メッセージ名は `操作名() : void` の形にする（例: `L1 -> L2 : 再生ボタンを押下する() : void`）。メッセージを受け取った側を `activate` / `deactivate` する。`alt` などの分岐の中で `activate` したものは、その分岐の中で `deactivate` する。
- クラス図: `class "クラス名" as C1 <<control>> { ... }` のようにステレオタイプを付ける。操作は `{method} <U+002B> 操作名() : void` と書く（`+ ` とそのまま書くと「+」の後ろの空白が消える）。クラスどうしは、使う側から使われる側へ向きのある矢印 `C1 --> C2` でつなぐ（画面 → 処理 → データ。処理どうしは呼び出す側 → 呼び出される側）。向きはシーケンス図のメッセージの向きとそろえる。`hide empty members` は書かない。
- 画面遷移図（ステートマシン図。`図/画面遷移図/` の2枚）: 仕様書の 10.1 画面一覧・10.2 の遷移の条件から描く。1枚に全部の遷移（24本）を入れると線が交差して読めないので、2枚に分ける（2026-11-24 決定。ユーザーの指示）：
  - `全体_画面遷移図`：メニュー・ミュージックリストなどから各画面へ移る遷移と、モード画面の間の遷移（「生成する」「設定を変更」「カスタムモードで編集する」）。アレンジ画面・ピアノロール画面は載せない（タブでしか入らない）。
  - `タブ切替_画面遷移図`：モード画面の中のタブの切り替え（設定／アレンジャー／ピアノロール。シンプルモードは設定／ピアノロール）と「ピアノロールを開く」「アレンジャーで →」。シンプルモード画面・シンプルモード生成後画面・カスタムモード画面・アレンジ画面・ピアノロール画面を載せる。
  - 2枚を合わせて 10.1 の画面・10.2 の遷移をすべて載せる。新しい遷移は、タブの切り替えならタブ切替、それ以外は全体に足す。
  - 画面は `state "<画面名>" as S<画面IDの番号>`（例: 画面ID `MENU-001` のメニュー画面は `state "メニュー画面" as S001`）。画面名は 10.1 の画面名と同じにする（画面IDは連番なので、`S001` から順に並ぶ）。
  - 各画面に `S001 : entry / …`（表示するもの）、`do / …`（その画面でする主な操作。なければ省く）、`exit / …`（離れ方）を書く。「メニューに戻る」（パンくず）の矢印は全画面から引くと読めなくなるので引かず、`exit / メニューに戻る` と書く。
  - 開始は `[*] --> S001 : 　アプリを起動する`（全体_画面遷移図だけ）。
  - 遷移の矢印の文（ラベル）は、利用者のアクションを「〜する」の形で書く（2026-11-24 決定。ユーザーの指示）：ボタンは `「<ボタン名>」ボタンを押下する`、タブは `<タブ名>タブを押下する`（メニュー画面の大きなボタンも同じく `「シンプルモード」ボタンを押下する`。「カード」とは書かない。2026-11-24 ユーザーの指示。読み手がイメージしにくいため）。行き先が条件で変わるときは `\n[条件]` を添える（例: `S005 -up-> S006 : 　設定タブを押下する\n　[シンプルモード・生成後]`）。長い文は1行15文字くらいで `\n` で改行し、各行の頭に全角の空白を1つ入れて線と文の間にすき間を作る（PlantUML は文を線のすぐ右に置く）。
  - 画面の中だけで終わる操作（再生・保存など）は矢印にしない。
  - 文字と線・文字どうし・外枠と線が重ならないようにする（2026-11-24 決定。ユーザーの指示。左の外枠に「カスタムモード」の線が沿い、文字が線に触れていたため）：
    - 画面は格子状に並べ、線をできるだけ短く・交差しないようにする。全体_画面遷移図は 上の段 メニュー、中の段 左から シンプルモード｜ミュージックリスト｜カスタムモード｜音楽クイズ｜設定、下の段 シンプルモード生成後。ミュージックリスト → シンプルモード・カスタムモードは横向き（`-left->` / `-right->`）にして同じ段に並べる。タブ切替_画面遷移図は 上の段 シンプルモード・カスタムモード、下の段 左から シンプルモード生成後｜ピアノロール｜アレンジ（`S002 -[hidden]-> S006` で生成後を下に置き、下の段の線は横向き）。戻る向きの縦の線は `-up->` で書く（`-->` のままだと段が崩れて線が長くなる）。
    - 画面の間の広さ（`nodesep 120`・`ranksep 180`。横向きの線が並ぶ所と、段の間の斜めの線が集まる所に文が離れて入るよう、横・縦とも広くしている。2026-11-24 にユーザーの指示で縦を 80 → 180 に広げた。メニュー画面から出る線の文どうし、シンプルモード画面のまわりの文どうしが近くて見づらかったため）と、外枠と中身の間の余白（`mainframe { Padding 30 }`）は共通設定 `astah-state-style.puml` に書いてある。
  - 線の折れ目を減らし、線の文を自分の線のすぐ横に置く（2026-11-24 決定。ユーザーの指示。PlantUML の線は遠回りしてかくかく折れ、文が線から離れてどの線の文か分かりにくかったため）。PlantUML ではそう引けないので、SVG に変換したあと `node docs/基本設計書/tools/state_layout.mjs`（リポジトリのルートで。画面遷移図のフォルダの SVG をすべて処理し、処理済みの SVG は変えない）で直す：
    - 折れ目は、画面の箱（から 8）・ほかの線（から 8。箱の縁の近くは除く）にぶつからない範囲で飛ばしてまっすぐにつなぐ。線はまっすぐな線分のまま（曲線にしない）。矢じりは最後の向きに合わせて描き直す。
    - 文は自分の線に沿わせて、線から 4 離して置く（2026-11-24 ユーザーの指示。斜めの線の横に横書きの文を置くと、線から離れて見え、隣の線の文と区別しにくかったため）。傾きが 60 度以内の線は、文を線と平行に傾けて線のすぐ上（入らなければ下）に置き、線の長さの 7 割に収まれば1行にまとめる（文の続きはつなぎ、条件の [...] の前にだけ全角の空白を入れる）。縦に近い線（60 度より急）は、傾けると読みにくいので横書きのまま線のすぐ横に置く。傾けた文は `<g transform="rotate(角度 cx cy)">` で包む（`label_overlap.mjs` はこの傾きも読んで重なりを数える）。線の中ほどに近く、ほかの線から離れた（どの線の文か迷わない）位置を選び、画面の箱・線・ほかの文と重ねず、ほかの文とは 30 以上離す（狭い位置は点数を下げる。2026-11-24 ユーザーの指示）。文の頭の全角の空白は外す。
    - 直した SVG は手で直さない。文の位置を変えたいときは .puml（文の改行・矢印の向き）を直して変換し直し、スクリプトをもう一度動かす。「置けない文」と出たら .puml の文を短くする。
    - 曲線（`linetype` を外す）は試したが、astah の見た目と違ううえ文は線から離れたままなので使わない。直角（`linetype ortho`）は文が線に重なるので使わない（2026-11-24 に試した）。
  - 直したら `node docs/基本設計書/tools/label_overlap.mjs docs/基本設計書/図/画面遷移図/*.svg` で「重なり 0 件」を確かめ、`node docs/基本設計書/tools/state_layout.mjs --png <スクラッチパッドのフォルダ>` で PNG を作って、文がどの線のものか分かるか・一番外側の線が外枠に触れていないかを目で確かめる（PlantUML の `-tpng` は直す前の見た目になるので使わない）。
- システム概要図・システム構成図（`図/システム図/システム概要図.puml`・`システム構成図.puml` の各1枚。2026-11-19 追加）: 配置図の部品（`actor` / `node` / `rectangle` / `database` / `storage` / `folder` / `artifact`）で描き、名前の前に OpenIconic のアイコン（`<&monitor{scale=3}>` など）を置いて、何の機器・ソフト・データかを絵でも分かるようにする。
  - システム概要図は仕様書の 3.1・3.2 から描く（利用者 → 画面 → アプリの状態 → 処理 → スピーカー・ファイルの流れ）。処理の名前は付録A に合わせ、機能ごとの細かさにはしない。
  - 線のラベルは、その線を通る主な依頼を短い動詞句ですべて書く（1つだけ書くと、ほかの流れがないように読める）。主語や出どころの画面名は線の向きで分かるので書かない（例: `UI --> P6 : 出題を頼む・回答を渡す`。2026-11-20 決定）。
  - 文のない線を残さない。両向きの線（`<-->`）の文は、処理を主語にして「〜を読み、〜を書き込む」のように書き、どちら向きに何が流れるか分かるようにする（例: `ST <--> P5 : 変更前の曲の内容を残し、\n元に戻すときに書き戻す`。2026-11-23 決定。ユーザーの指示。「変更前の曲の内容」だけではどこからどこへの線か分からなかったため）。
  - 線の文は、PlantUML が線のすぐ横に置けるよう、線を短く・交わらないように並べる（2026-11-23 決定。ユーザーの指示。長い線が並ぶと「音を出す」がどの線の文か分からなかった）：処理は見えない線（`-[hidden]right-`）で左から 履歴管理・端末の設定・曲の管理・書き出し・再生・自動作曲・クイズ出題 の順に並べ、スピーカー・出力フォルダ・曲ファイルは Toniq の枠の下の段（`LIST -[hidden]down- FILE` など）の、使う処理の下に置く。クイズ問題マスタはクイズ出題の右に置いて横の線（`QDB -left-> P6`）にし、「出題を頼む・回答を渡す」の文と重ならないようにする。部品の間は `skinparam nodesep 90`・`skinparam ranksep 120` で広げ、線の文の頭には全角の空白を1つ入れて線と文の間にすき間を作る（PlantUML は文を線のすぐ右に置くので、そのままでは文の左端が線に触れる。2026-11-23 決定。ユーザーの指示）。部品・線を足したら PNG にして、文がどの線のものか分かるか・線と重なっていないかを確かめる。
  - ロバストネス図の `robustness_labels.mjs` はこの図には使わない（四角・データベースの形を読めず、文が縦になったり部品に重なったりする。2026-11-23 に試した）。
  - 問題を作るのは処理「クイズ出題」で、音楽クイズ画面は問題を表示して回答を受け付けるだけ（Q01-1 のロバストネス図・シーケンス図と同じ分け方。採点は Q01-1 では別の処理「採点」、システム概要図では「クイズ出題」にまとめる）。「クイズ出題」を「クイズ回答処理」などに名前を変えない。回答は仕様書・図とも「回答」と書く（「解答」は使わない）。
  - スピーカー・ヘッドホンから利用者へ戻る線（「聴く」など）は引かない。図は利用者の操作から音・ファイルが出るまでの流れだけを描く（2026-11-23。ユーザーの指示）。
  - 中に部品を入れる入れ物（`Toniq（Windows PC で動くデスクトップアプリ）` の四角など）の名前は、枠の左上に置く。入れ物に `<<box>>` を付ける（`rectangle "…" as SYS <<box>> { … }`。左寄せの設定とステレオタイプの文字を隠す設定は astah-system-style.puml にある）。中の部品の名前は今までどおり中央（2026-11-23。ユーザーの指示。中央に置くと、すぐ外側の枠の名前か中の部品の名前か分かりにくいため）。
  - システム構成図は仕様書の 4.2 システム構成表から描く。各部品の名前の先頭に構成表の図番号（①②…）を付け、構成表の行と1対1にする。構成表に載せない開発用のもの（開発ツール・ビルドの道具）は描かない。利用者は番号を付けずに描いてよい。
- ER図（`図/ER図/ER図.puml` の1枚。2026-11-19 追加）: 仕様書の 12.1 テーブル定義（主キー・主な項目に書いた参照先）から描く。エンティティ・キー・線の種類は IDEF1X の記法（リポジトリのルートの `ER図.png` の形）、多重度は UML の表記（下）にする。`!include ../astah-er-style.puml`、枠（mainframe）は付けない。色はクラス図と同じ薄い黄色（#FFFFCC）・太い黒枠。
