# 基本設計書の作成手順

Toniq の基本設計書（`作成ファイル/04_2026_卒研_基本設計書(R4SA_アプリオリ).docx`）を仕上げるまでの手順です。
システムはほかのメンバーが更新し続けていて、機能や画面の数もまだ変わります。そこで、**仕様書（.md）と図（.puml / .svg）を Git で管理しながら更新**し、docx はそこからスクリプトで作ります（「5. docx を作る」）。

## 1. 機能IDを決める（済）

機能一覧の「グループID（B01 など）＋枝番」で、機能ごとに一意の ID を付けます。

- 枝番は、機能一覧に並んでいる順に 1 から振る（例: B01-1 BPM選択、B01-2 テンポ選択 …）。
- 一度付けた ID は変えない。機能を足したらグループの最後の番号の次を使い、機能を消しても番号は使い回さない。
- 新しいグループが要るときは、新しいグループID（例: `M01` 曲の管理）を作る。

付けた ID は [仕様書.md](仕様書.md) の「5.1 機能一覧」にあります（48機能。うち未実装は K01-3 キー・スケール試聴と A01-4 MP3エクスポート）。ID の一覧は仕様書だけに書き、この手順書には写しません。

元の機能一覧（31機能）は、並んでいる順に枝番を振りました。元の一覧になかった実装済みの機能は、次のように足しました。

- 既存のグループの最後に追加：C01-6 コード音色選択、A01-6 再生開始位置選択
- 新しいグループを追加：M01 曲の管理（M01-1〜M01-8）、H01 履歴（H01-1）、U01 設定（U01-1〜U01-6）

## 2. 仕様書（仕様書.md）を作る

### 2-1. 構成

docx の章立てに合わせます。図の章は、5章（機能設計）と10章（画面設計）の間の 6〜9章です（作成済みの docx と同じ形。2026-11-10 決定）。docx では図の種類ごとに章を分け（6 ユースケース図、7 ロバストネス図、8 シーケンス図、9 クラス図）、その中を機能IDごとの節にします。仕様書.md では 7〜9章を1つの章にまとめ、機能IDごとの節に3つの図を並べます（docx を作るときにスクリプトが3つの章に分ける）。

```
仕様書.md
├─ 基準のコード（どのコミット時点のコードで書いたか）
├─ 1〜4章  システム構築方針・制約条件・システム概要・システム構成
├─ 5章     機能設計（5.1 機能一覧／5.2 機能ごとの定義表）
├─ 6章     ユースケース図（全体とグループごとに SVG へのリンクを書く）
├─ 7〜9章  ロバストネス図／シーケンス図／クラス図（1つの章にまとめ、機能IDごとに SVG へのリンクを書く）
├─ 画面設計・帳票設計・データベース設計・コード設計・性能・運用・信頼性・保守
└─ 付録    名前の対応表（図の日本語名 ⇔ コードのファイル名）
```

- 図は `![ロバストネス図](図/ロバストネス図/B01-1_BPM選択機能_ロバストネス図.svg)` のように図へのリンクを書く（画像のデータは入れず、SVG ファイルの場所を指すだけ）。VS Code のプレビューで図もいっしょに見られる。図を実際に貼り付けるのは docx を作るとき（`tools/build_docx.ps1` がこのリンクをたどる）。
- 未実装の機能も機能一覧には残し、「状況」の列に「未実装」と書く。図は実装されてから作る。

### 2-2. 基準のコード

仕様書の先頭に、書いたときの `main` のコミットを記録します。

```markdown
> 基準のコード：main のコミット `xxxxxxx`（2026-11-xx）
```

次に更新するときは、ここから後の変更だけを調べます（「4. コードが更新されたとき」）。

### 2-3. 名前の対応表

図で使う日本語の名前と、コードのファイル名の対応を1つの表にまとめます。どの図もこの表の名前を使います。

| 種類 | 図の名前 | コード |
|---|---|---|
| 画面 | シンプルモード画面 | `src/ui/SimpleScreen.ts` |
| 処理 | 再生 | `src/engine/Playback.ts` |
| データ | コード進行マスタ | `src/data/chord_progressions.json` |
| … | … | … |

### 2-4. Claude Code への頼み方（例）

> `main` の最新のコードを読んで、`docs/基本設計書/仕様書.md` を作って。章立ては「作成ファイル」の docx に合わせ、機能IDは `基本設計書の作成手順.md` の案を使って。基準のコミットと名前の対応表も書いて。

## 4. コードが更新されたとき

コードのコミットのたびではなく、**区切りのよいとき**（`main` へのマージのあと、週1回など）にまとめて更新します。

1. 仕様書の「基準のコード」のコミットから、今の `main` までの変更を見る。
   ```
   git log --oneline <基準のコミット>..main
   git diff --stat <基準のコミット> main -- src index.html
   ```
2. 変更の中身を、次のどれに当たるか分ける。
   - 機能が増えた・減った・動きが変わった → 機能一覧・機能定義を直し、関係する図を直す
   - 画面の部品が変わった → 画面設計を直す
   - JSON の項目が変わった → データベース設計・コード設計を直す
   - 見た目・内部の整理だけ → 仕様書は直さなくてよい
3. 仕様書（.md）を直す。ID は変えない（機能が増えたら新しい ID を付ける）。
4. 関係する図の `.puml` を直し、SVG を作り直す。
5. 仕様書の「基準のコード」を今の `main` のコミットに書き換える。
6. 仕様書と図をまとめてコミットする（コミットはユーザーが行う）。

Claude Code への頼み方（例）：

> `仕様書.md` の基準のコミットから今の `main` までの変更を調べて、仕様書と図を更新して。仕様書を直さなくてよい変更も一覧にして報告して。

## 5. docx を作る

仕様書.md と図から、`作成ファイル/04_2026_卒研_基本設計書(R4SA_アプリオリ)_仕様書から作成.docx` をスクリプトで作ります。書式（表紙・改訂履歴・目次・見出し・表・裏表紙）は `作成ファイル/04_2026_卒研_基本設計書(R4SA_アプリオリ).docx`（手本）のものを使います。

**docx は直接直さず、仕様書.md・図を直してから作り直します。** 一部だけ直したいときも同じです（作り直しは数分。docx を直接直すと仕様書.md とずれ、次に作り直したときに直した内容が消える）。

### 5-1. 作り方

リポジトリのルートで実行します。必要なもの：Java（`tools/plantuml.jar`）、Python（`py`）、Microsoft Word（365 版）。

```
powershell -ExecutionPolicy Bypass -File "docs/基本設計書/tools/build_docx.ps1" -Rev 03 -RevNote "改訂の概要"
```

| 引数 | 内容 |
|---|---|
| `-Rev` | 改訂履歴に足す版数（例 `03`）。手本の 01 の行の下に1行足す |
| `-RevNote` | 改訂履歴の改訂の概要（例 `仕様書.md（基準：main xxxxxxx）の内容で改訂。…`） |
| `-Date` | 表紙と改訂履歴の日付（省略時は今日。例 `2026/11/20`） |
| `-Out` | 出力先（省略時は上の docx を上書き） |
| `-SkipPng` | 図を変えていないとき、PNG の作り直しを省く |

スクリプトがすること：

1. 図（`.puml`）を PNG にする（`%TEMP%\toniq_build_docx\png`）。docx には図を SVG と PNG の両方で入れる（SVG を表示できない Word では PNG が出る）。
2. `tools/build_docx.py` で仕様書.md を手本の書式の docx に変換する（下書き）。
3. Word を裏で開いて目次とページ番号を更新し、docx として保存する。

全体で2〜3分かかります（PNG の作成 約1分、Word 約1分）。

できたら docx を Word で開いて、表紙・改訂履歴・目次・機能定義の表・図のページを目で確かめます。PDF はスクリプトでは作りません（`powershell -File` から Word の PDF 書き出しを呼ぶと戻ってこなかったため）。Claude Code に確かめてもらうときは、スクリプトの外で、PowerShell から Word を開いて `ExportAsFixedFormat(<PDFのパス>, 17)` で PDF にしてからページを画像にして見てもらいます（この方法なら約1分で終わる）。

### 5-2. 仕様書.md の書き方の決まり（変換で使っている）

`build_docx.py` は仕様書.md の形を見て変換します。次の形を崩すと docx が崩れます。

| 仕様書.md | docx |
|---|---|
| `##`（章）| 見出し1（改ページ）。章番号は Word が付けるので、見出しの番号（`5.` など）は外す |
| `###` / `####` | 見出し2 / 見出し3。`#### B01-1 BPM選択機能` のように機能IDで始まる `####` は機能定義の節 |
| 機能定義の節の「項目 \| 内容」の表 | 手本の機能定義の表（19行）。行は `事前条件` `事後条件` `入力` `出力` `機能説明` `備考` を使う |
| 入力・出力の値 | `画面：…／ファイル：…` のように `画面` `帳票` `データベース` `ファイル` `その他` で区切る（書かなかった区分は「なし」）。区切りがなければ全部「その他」 |
| 「5.1 機能一覧」の `機能ID \| 機能名 …` の表 | 機能定義の表の機能名に使う |
| 6章（ユースケース図）の `####` | 見出し2 |
| 「7. ロバストネス図／8. シーケンス図／9. クラス図」の章（次の `##` の章の前まで） | 図の種類ごとの3つの章（ロバストネス図／シーケンス図／クラス図）に並べ替える。各節の `![ロバストネス図](…svg)` のように、alt に図の種類を書く。`全体のクラス図` の節はクラス図の章の先頭 |
| 16章の `節 \| 内容` の表 | 節ごとの見出し2＋本文 |
| 付録A | 番号なしの見出し。付録B・C は docx に入れない |
| その他の表 | 一般の表（短い列は折り返さない幅にし、残りを長い列で分ける） |
| `>` の引用・`---` | docx に入れない |

### 5-3. 注意

- `build_docx.py` は手本の docx の本文を段落・表の並びに分け、**番号で場所を決めて**使っています（表紙〜目次 = 0〜148、裏表紙 = 460〜、機能定義の表 = 203、改訂履歴 = 33、表紙の日付 = 23）。手本の docx を編集すると番号がずれるので、そのときは `build_docx.py` の番号を見直します（ずれると assert で止まる）。
- 改訂履歴は手本の 01 の行の下に1行足すだけです。版を重ねて 02・03 … と行を残したいときは、`build_docx.py` の改訂履歴の部分を直します。
- 目次の章番号が10章以降で崩れないよう、目次1のタブ位置を広げています。改訂履歴・目次の後の空行は、白紙のページができるので消しています。
- 図の章の前置きの文（未実装の機能の扱いなど）は `build_docx.py` の `FIG_INTRO` と 6章の置き換えの文に書いてあります。機能が実装されたら直します。
- 付録の名前の対応表（付録A）は、docx に載せるかどうかをチームで決める。
- できた docx は約14MB です。リポジトリが公開されているので、push するのは提出版など区切りのときだけにします。

### 5-4. Claude Code への頼み方（例）

> 仕様書.md と図を更新したので、`基本設計書の作成手順.md` の「5. docx を作る」に従って docx を作り直して。版数は 03、改訂の概要は「…」。できたら PDF で表紙・目次・図のページを確かめて。
