# 基本設計書の作成手順

Toniq の基本設計書（`作成ファイル/04_2026_卒研_基本設計書(R4SA_アプリオリ).docx`）を仕上げるまでの手順です。
システムはほかのメンバーが更新し続けていて、機能や画面の数もまだ変わります。そこで、**仕様書（.md）と図（.puml / .svg）を Git で管理しながら更新**し、docx はそこからスクリプトで作ります（「5. docx を作る」）。

## 1. 機能IDを決める（済）

機能一覧の「グループID（B01 など）＋枝番」で、機能ごとに一意の ID を付けます。

- 枝番は、機能一覧に並んでいる順に 1 から振る（例: B01-1 BPM選択、B01-2 テンポ選択 …）。
- 一度付けた ID は変えない。機能を足したらグループの最後の番号の次を使い、機能を消しても番号は使い回さない。
- 新しいグループが要るときは、新しいグループID（例: `M01` 曲の管理）を作る。

付けた ID は [仕様書.md](仕様書.md) の「5.1 機能一覧」にあります（57機能。未実装の機能はなし。2026-11-12、基準 main `de538b7` 時点）。ID の一覧は仕様書だけに書き、この手順書には写しません。

元の機能一覧（31機能）は、並んでいる順に枝番を振りました。元の一覧になかった実装済みの機能は、次のように足しました。

- 既存のグループの最後に追加：C01-6 コード音色選択、A01-6 再生開始位置選択
- 新しいグループを追加：M01 曲の管理（M01-1〜M01-8）、H01 履歴（H01-1）、U01 設定（U01-1〜U01-6）
- その後の追加・削除は仕様書.md の付録C（例：2026-11-12 に M01-9〜M01-11 を追加、U01-7 を削除して欠番）

## 2. 仕様書（仕様書.md）を作る

### 2-1. 構成

docx の章立てに合わせます。図の章は、5章（機能設計）と10章（画面設計）の間の 6〜9章です（作成済みの docx と同じ形。2026-11-10 決定）。docx では図の種類ごとに章を分け（6 ユースケース、7 ロバストネス図、8 シーケンス図、9 クラス図）、その中を機能IDごとの節にします。仕様書.md では 7〜9章を1つの章にまとめ、機能IDごとの節に3つの図を並べます（docx を作るときにスクリプトが3つの章に分ける）。

```
仕様書.md
├─ 基準のコード（どのコミット時点のコードで書いたか）
├─ 1〜4章  システム構築方針・制約条件・システム概要・システム構成
├─ 5章     機能設計（5.1 機能一覧／5.2 機能ごとの定義表）
├─ 6章     ユースケース
│            6.1 ユースケース図（全体とグループごとに SVG へのリンクを書く）
│            6.2 ユースケース記述（グループごとに、機能ごとの記述の表）
├─ 7〜9章  ロバストネス図／シーケンス図／クラス図（1つの章にまとめ、機能IDごとに SVG へのリンクを書く）
├─ 画面設計・帳票設計・データベース設計・コード設計・性能・運用・信頼性・保守
└─ 付録    名前の対応表（図の日本語名 ⇔ コードのファイル名）
```

- 図は `![ロバストネス図](図/ロバストネス図/B01-1_BPM選択機能_ロバストネス図.svg)` のように図へのリンクを書く（画像のデータは入れず、SVG ファイルの場所を指すだけ）。VS Code のプレビューで図もいっしょに見られる。図を実際に貼り付けるのは docx を作るとき（`tools/build_docx.ps1` がこのリンクをたどる）。
- 6.2 ユースケース記述は、6.1 の図と同じグループごとに `#### B01_曲の基本設定システム`（グループID_システム名。2026-11-12 変更）の節を置き、その中に機能ごとの `##### B01-1 BPM選択機能` の節と次の表を書く（2026-11-11 決定。作成済みの他チームの設計書の「ユースケース図 → ユースケース記述」の形に合わせた）。5.2 の機能（「（未実装）」の機能を除く）と1対1にし、見出しは 5.2 と同じ文字にする。
  ```
  | 項目 | 記述 |
  |---|---|
  | 作成日 | 2026/11/11 |
  | 版数 | 1 |
  | 作者 | 西薗 |
  | ユースケース名 | BPM選択機能 |
  | 概要 | BPMノブで曲のテンポ（BPM）を指定する機能 |
  | 主アクタ | 利用者 |
  | 支援アクタ | なし |
  | 事前条件 | … |
  | 事後条件 | … |
  | トリガー | BPMノブが操作される |
  | 基本フロー | 1. 利用者は …<br>2. システムは … |
  | 代替フロー | 3a. 再生中の場合、システムは … |
  | 例外フロー | なし |
  | 備考・注記 | … |
  ```
  - 15行すべてを書く（ない行があると docx を作るときに止まる）。書くことがない行は「なし」。
  - 事前条件・事後条件は 5.2 の機能定義に合わせるが、状態の項目名（`bpm` など）は使わず日本語で書く。
  - 基本フローは「利用者は …する」「システムは …する」の文を `1.` から番号を付けて `<br>` で区切る。代替フロー・例外フローは分かれる基本フローの番号に `a` `b` を付ける（例 `3a. 再生中の場合、…`）。例外フローは操作が先へ進めない・取り消される流れ。

  - **推測で書かない。順番は「コード → 5.2 → 6.2」**（2026-11-11 決定）。フローの分かれ道（確認ダイアログと取り消し、押せなくなる条件、失敗・空のときの通知、再生中かどうか、もう一度押したとき）は先に `origin/main` のコードで確かめて 5.2 の機能説明・備考に足し、6.2 は 5.2 に書いてあることだけで書く。コードで確かめられない動きは書かずに「要確認」として報告し、アプリを動かして確かめてから足す（手順は `/update-spec` の「3. 仕様書.md を直す」）。

## 5. docx を作る

仕様書.md と図から、`作成ファイル/04_2026_卒研_基本設計書(R4SA_アプリオリ)_仕様書から作成.docx` をスクリプトで作ります。書式（表紙・改訂履歴・目次・見出し・表・裏表紙）は `作成ファイル/04_2026_卒研_基本設計書(R4SA_アプリオリ).docx`（手本）のものを使います。

**docx は直接直さず、仕様書.md・図を直してから作り直します。** 一部だけ直したいときも同じです（作り直しは数分。docx を直接直すと仕様書.md とずれ、次に作り直したときに直した内容が消える）。

### 5-1. 作り方

リポジトリのルートで実行します。必要なもの：Java（`tools/plantuml.jar`）、Python（`py`）、Node.js、Microsoft Word（365 版）、Edge か Chrome（ロバストネス図の PNG）。`build_docx.ps1` はロバストネス図の線の文を置き直し（`robustness_labels.mjs`。処理済みなら何もしない）、docx に入れる代わりの PNG も、ロバストネス図だけは置き直した SVG から作ります（PlantUML の PNG は文の位置が古いため）。

まず事前の確認をします（必要なもの・出力先の docx が閉じているか・仕様書が origin/main に追いついているか・付録C の「要：」・5.2 と 6.2 の対応・未実装の機能と `build_docx.py` の文を `[OK]` / `[NG]` で出し、次の版数と改訂の概要の材料も出す）。

```
py docs/基本設計書/tools/preflight.py
```

`[NG]` がなければ docx を作ります。

```
powershell -ExecutionPolicy Bypass -File "docs/基本設計書/tools/build_docx.ps1" -Rev 04 -RevNote "改訂の概要"
```

| 引数 | 内容 |
|---|---|
| `-Rev` | 改訂履歴に足す版数（例 `03`）。`tools/改訂履歴.tsv` に足し（同じ版なら上書き）、手本の 01 の行の下に 02 から順に並べる。表紙の文書番号の末尾「(01)」もこの版数にする |
| `-RevNote` | 改訂履歴の改訂の概要（例 `仕様書.md（基準：main xxxxxxx）の内容で改訂。…`） |
| `-Date` | 表紙と改訂履歴の日付（省略時は今日。例 `2026/11/20`） |
| `-Out` | 出力先（省略時は上の docx を上書き） |
| `-SkipPng` | PNG を作り直さない（ふつうは不要。図が変わったときだけ自動で作り直す） |
| `-ForcePng` | 図が変わっていなくても PNG を作り直す |

スクリプトがすること：

1. 図（`.puml`）を PNG にする（`%TEMP%\toniq_build_docx\png`）。いちばん新しい `.puml` が いちばん古い PNG より新しいとき（と PNG がないとき）だけ作り直す。docx には図を SVG と PNG の両方で入れる（SVG を表示できない Word では PNG が出る）。
2. `tools/build_docx.py` で仕様書.md を手本の書式の docx に変換する（下書き）。
3. Word を裏で開いて目次とページ番号を更新し、docx として保存する。
4. `tools/check_docx.py` で、できた docx の表紙の文書番号・日付、改訂履歴、目次、機能定義・ユースケース記述の表の数（仕様書と比べる）、図の数を確かめ、`[OK]` / `[NG]` で出す（NG があれば失敗で終わる）。

全体で約2分かかります（図を変えたときは PNG の作成で +1分）。

見た目（崩れ・改ページ）は、できた docx を Word で開いて目で確かめます。PDF は作りません（Word の PDF 書き出しは、`powershell -File` からでも外からでも戻ってこないことがあった。2026-11-11 には2回とも10分以上返らなかった）。

### 5-2. 仕様書.md の書き方の決まり（変換で使っている）

`build_docx.py` は仕様書.md の形を見て変換します。次の形を崩すと docx が崩れます。

| 仕様書.md | docx |
|---|---|
| `##`（章）| 見出し1（改ページ）。章番号は Word が付けるので、見出しの番号（`5.` など）は外す |
| `###` / `####` | 見出し2 / 見出し3。5.2 の `#### B01_曲の基本設定システム` はシステムの節 |
| 5.2 の `#####`（`##### B01-1 BPM選択機能` のように機能IDで始まる） | 機能定義の節。見出し4で、docx の見出しは機能名だけ（`BPM選択機能`。機能IDと最後の「（追加）」「（未実装）」は外す。機能IDは機能定義の表の「機能ID」の行に入る） |
| 表の直前の `**…**` だけの行 | 表の1行目（列を全部結合し、網掛けした行）。5.1 のシステム名、10.3.2 の画面名に使う |
| 機能定義の節の「項目 \| 内容」の表 | 手本の機能定義の表（19行）。行は `事前条件` `事後条件` `入力` `出力` `機能説明` `備考` を使う |
| 入力・出力の値 | `画面：…／ファイル：…` のように `画面` `帳票` `データベース` `ファイル` `その他` で区切る（書かなかった区分は「なし」）。区切りがなければ全部「その他」 |
| 「5.1 機能一覧」の `機能ID \| 機能名 \| 画面 \| 説明` の表 | 一般の表として載せ、機能定義の表の機能名にも使う（1・2列目が `機能ID` `機能名` であること） |
| 6章の `###`（6.1 ユースケース図・6.2 ユースケース記述）／`####`（図名・機能グループ）／`#####`（機能） | 見出し2／見出し3／見出し4。`#####` の見出しは機能名だけ（機能IDと最後の「（追加）」などは外す） |
| 6.2 の「項目 \| 記述」の表 | ユースケース記述の表（1行目が 作成日・版数・作者、2行目から ユースケース名〜備考・注記）。手本の docx にない形なので `build_docx.py` の `usecase_table` で組み立てる。セルの中の `<br>` は改行 |
| 「7. ロバストネス図／8. シーケンス図／9. クラス図」の章（次の `##` の章の前まで） | 図の種類ごとの3つの章（ロバストネス図／シーケンス図／クラス図）に並べ替える。`### B01_曲の基本設定システム` は見出し2、`#### B01-1_BPM選択機能` は見出し3（「_」を全角スペースにして `B01-1　BPM選択機能`）。各節の `![ロバストネス図](…svg)` のように、alt に図の種類を書く。`全体のクラス図` の節はクラス図の章の先頭 |
| 16章の `節 \| 内容` の表 | 節ごとの見出し2＋本文 |
| 付録A | 番号なしの見出し。付録B・C は docx に入れない |
| その他の表 | 一般の表（短い列は折り返さない幅にし、残りを長い列で分ける） |
| `>` の引用・`---` | docx に入れない |

### 5-3. 注意

- `build_docx.py` は手本の docx の本文を段落・表の並びに分け、**番号で場所を決めて**使っています（表紙〜目次 = 0〜148、裏表紙 = 460〜、機能定義の表 = 203、改訂履歴 = 33、表紙の日付 = 23）。手本の docx を編集すると番号がずれるので、そのときは `build_docx.py` の番号を見直します（ずれると assert で止まる）。
- 改訂履歴の 02 以降は `tools/改訂履歴.tsv`（1行 = 版数・日付・改訂の概要をタブで区切る）に残します。`build_docx.py` が今回の版を足して書き戻し、全部の行を 01 の下に並べます。過去の行の概要を直したいときは、このファイルを直してから作り直します。
- 表紙の文書番号（`KCSKA-R4SA-アプリオリ(01)`）の末尾は版数です。`-Rev` に合わせて書き換えます。
- 出力先の docx を Word で開いたままだと、`build_docx.ps1` は最初に止まります（閉じてから実行する）。
- 目次の章番号が10章以降で崩れないよう、目次1のタブ位置を広げています。見出し1〜4の番号のあとのタブ位置も広げています（`numbering.xml`。手本のままだと「5.2.10」「7.32.」のように番号が2桁になると、番号と名前の間が空かない）。改訂履歴・目次の後の空行は、白紙のページができるので消しています。
- 図の章の前置きの文は `build_docx.py` の `FIG_INTRO` と 6章の置き換えの文に書いてあります。未実装の機能ができたら「未実装の … は実装後に作成する。」の文を足し、実装されたら外します（2026-11-11 時点で未実装の機能はないので、この文は入れていない）。
- 付録の名前の対応表（付録A）は、docx に載せるかどうかをチームで決める。
- できた docx は約18MB です（版 03）。リポジトリが公開されているので、push するのは提出版など区切りのときだけにします。
