# 基本設計書の作成手順

Toniq の基本設計書（`作成ファイル/04_2026_卒研_基本設計書(R4SA_アプリオリ).docx`）を仕上げるまでの手順です。
システムはほかのメンバーが更新し続けていて、機能や画面の数もまだ変わります。そこで、完成までは **仕様書（.md）と図（.puml / .svg）を Git で管理しながら更新**し、システムが固まったら docx に移します。

## 1. 機能IDを決める（済）

機能一覧の「グループID（B01 など）＋枝番」で、機能ごとに一意の ID を付けます。

- 枝番は、機能一覧に並んでいる順に 1 から振る（例: B01-1 BPM選択、B01-2 テンポ選択 …）。
- 一度付けた ID は変えない。機能を足したらグループの最後の番号の次を使い、機能を消しても番号は使い回さない。
- 新しいグループが要るときは、新しいグループID（例: `M01` 曲の管理）を作る。

付けた ID は [仕様書.md](仕様書.md) の「5.1 機能一覧」にあります（48機能。うち未実装は K01-3 キー・スケール試聴と A01-4 MP3エクスポート）。ID の一覧は仕様書だけに書き、この手順書には写しません。

元の機能一覧（31機能）は、並んでいる順に枝番を振りました。元の一覧になかった実装済みの機能は、次のように足しました。

- 既存のグループの最後に追加：C01-6 コード音色選択、A01-6 再生開始位置選択
- 新しいグループを追加：M01 曲の管理（M01-1〜M01-8）、H01 履歴（H01-1）、U01 設定（U01-1〜U01-6）

## 2. 仕様書（仕様書.md）を作る

### 2-1. 構成

docx の章立てに合わせます。図の章は、手本（他チームの基本設計書）と同じく図の種類ごとに章を分け、その中を機能IDごとの節にします。

```
仕様書.md
├─ 基準のコード（どのコミット時点のコードで書いたか）
├─ 1〜4章  システム構築方針・制約条件・システム概要・システム構成
├─ 5章     機能設計（5.1 機能一覧／5.2 機能ごとの定義表）
├─ 図の章  ユースケース図／ロバストネス図／シーケンス図／クラス図（機能IDごとに SVG を埋め込む）
├─ 画面設計・帳票設計・データベース設計・コード設計・性能・運用・信頼性・保守
└─ 付録    名前の対応表（図の日本語名 ⇔ コードのファイル名）
```

- 図は `![ロバストネス図](図/ロバストネス図/B01-1_BPM選択機能_ロバストネス図.svg)` のように埋め込む。VS Code のプレビューで図もいっしょに見られる。
- 未実装の機能も機能一覧には残し、「状況」の列に「未実装」と書く。図は実装されてから作る。

### 2-2. 基準のコード

仕様書の先頭に、書いたときの `main` のコミットを記録します。

```markdown
> 基準のコード：main のコミット `xxxxxxx`（2026-11-xx）
```

次に更新するときは、ここから後の変更だけを調べます（「4. コードが更新されたとき」）。

### 2-3. 名前の対応表

図で使う日本語の名前と、コードのファイル名の対応を1つの表にまとめます。どの図もこの表の名前を使います。

| 種類 | 図の名前 | コード |
|---|---|---|
| 画面 | シンプルモード画面 | `src/ui/SimpleScreen.ts` |
| 処理 | 再生 | `src/engine/Playback.ts` |
| データ | コード進行マスタ | `src/data/chord_progressions.json` |
| … | … | … |

### 2-4. Claude Code への頼み方（例）

> `main` の最新のコードを読んで、`docs/基本設計書/仕様書.md` を作って。章立ては「作成ファイル」の docx に合わせ、機能IDは `基本設計書の作成手順.md` の案を使って。基準のコミットと名前の対応表も書いて。

## 3. 図を作る

### 3-1. 古い図を消す（済）

2026-11-05 に作った図（`101_…` などの番号付きの名前、コードの識別子で書いたもの）は、新しい決まりに合わないので消しました（2026-11-05）。

### 3-2. 作る図

| 図 | 単位 | ファイル名の例 |
|---|---|---|
| ユースケース図 | 全体1枚＋グループごと | `全体_楽曲生成システムToniq_ユースケース図`、`B01_BPM・曲の基本設定_ユースケース図` |
| ロバストネス図 | 実装済みの機能ごと | `B01-1_BPM選択機能_ロバストネス図` |
| シーケンス図 | 実装済みの機能ごと | `B01-1_BPM選択機能_シーケンス図` |
| クラス図 | 全体1枚＋実装済みの機能ごと | `全体_クラス図`、`B01-1_BPM選択機能_クラス図` |

### 3-3. 手順

1. 仕様書の機能定義と名前の対応表を見て `.puml` を書く（書き方は [図/CLAUDE.md](図/CLAUDE.md)）。
2. リポジトリのルートで SVG に変換する。
   ```
   java -jar tools/plantuml.jar -tsvg -charset UTF-8 "docs/基本設計書/図/**/*.puml"
   ```
3. `.svg` に「Syntax Error」が含まれていないか確かめる。
4. 仕様書の図の章に SVG を埋め込む。

### 3-4. Claude Code への頼み方（例）

> `仕様書.md` をもとに、図/CLAUDE.md の決まりに従って、ロバストネス図・シーケンス図・クラス図を実装済みの機能ごとに作り直して。SVG にも変換して、仕様書に埋め込んで。

## 4. コードが更新されたとき

コードのコミットのたびではなく、**区切りのよいとき**（`main` へのマージのあと、週1回など）にまとめて更新します。

1. 仕様書の「基準のコード」のコミットから、今の `main` までの変更を見る。
   ```
   git log --oneline <基準のコミット>..main
   git diff --stat <基準のコミット> main -- src index.html
   ```
2. 変更の中身を、次のどれに当たるか分ける。
   - 機能が増えた・減った・動きが変わった → 機能一覧・機能定義を直し、関係する図を直す
   - 画面の部品が変わった → 画面設計を直す
   - JSON の項目が変わった → データベース設計・コード設計を直す
   - 見た目・内部の整理だけ → 仕様書は直さなくてよい
3. 仕様書（.md）を直す。ID は変えない（機能が増えたら新しい ID を付ける）。
4. 関係する図の `.puml` を直し、SVG を作り直す。
5. 仕様書の「基準のコード」を今の `main` のコミットに書き換える。
6. 仕様書と図をまとめてコミットする（コミットはユーザーが行う）。

Claude Code への頼み方（例）：

> `仕様書.md` の基準のコミットから今の `main` までの変更を調べて、仕様書と図を更新して。仕様書を直さなくてよい変更も一覧にして報告して。

## 5. 完成したら docx に移す

システムが固まったら、仕様書.md と SVG をもとに `作成ファイル/04_2026_卒研_基本設計書(R4SA_アプリオリ).docx` を仕上げます。

1. 仕様書の各章を、docx の同じ章・表に写す（章立てと表の形をそろえてあるので、ほぼ写すだけ）。
2. 図は SVG のまま Word に貼る（Microsoft 365 版の Word は SVG に対応している）。
3. 目次を更新し、章番号のずれ・テンプレートの名残り（記入用仕様書の「文書の不備」）を直す。
4. 付録の名前の対応表は、docx に載せるかどうかをチームで決める。
