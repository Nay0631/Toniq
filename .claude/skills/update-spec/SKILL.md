# 仕様書.md の更新

`docs/基本設計書/仕様書.md` を、コードの変更に合わせて更新する。毎回この手順どおりに行い、手順を飛ばさない。
背景と決まりは `docs/基本設計書/基本設計書の作成手順.md`（とくに「0. 決まっていること」「4. コードが更新されたとき」「5-2. 仕様書.md の書き方の決まり」）にある。最初に読む。

## 0. 前提（必ず守る）

- **見るのは `origin/main` のコードだけ。** ローカルの `main` ブランチや作業中のブランチ・作業ツリーは古いことがあるので使わない。
- 作業の最初に `git fetch origin` を実行する（失敗したら止めてユーザーに知らせる）。
- コードは `git show origin/main:<パス>`、差分は `git diff <BASE> origin/main -- <パス>` で読む。ブランチの切り替え（checkout / switch）はしない。
- 引数でコミットが渡されたら、`origin/main` の代わりにそれを HEAD として使う。
- 図（`docs/基本設計書/図/`）・`tools/`・docx は変えない。図の直しは `update-diagrams` スキルで行う。
- コミット・push はしない。

## 1. 調べる範囲を決める

1. 仕様書.md の先頭の行 `> **基準のコード**：`main` のコミット `xxxxxxx`` から BASE を読む。
2. `git rev-parse --short origin/main` で HEAD を決める。
3. BASE と HEAD が同じなら「前回から変更なし」と報告して終わる。
4. 次を実行して変更の全体を見る。
   ```
   git log --oneline <BASE>..origin/main
   git diff --stat <BASE> origin/main -- src index.html electron CLAUDE.md
   ```
   `CLAUDE.md` の差分は設計の決まりの変更をまとめて書いてあるので、最初に読む（変更の意図をつかむため）。

## 2. 変更を分ける

変更したファイル（またはコミット）ごとに、次のどれに当たるかを決めて表にする（この表は最後の報告に使う）。

| 分類 | 仕様書で直すところ |
|---|---|
| 機能が増えた・減った・動きが変わった | 5.1 機能一覧、5.2 機能定義、付録A 名前の対応表。**図の更新が必要**として機能IDを控える |
| 画面の部品が変わった | 10. 画面設計（と関係する機能定義の入力・出力）。画面が増えたら 10.1 に「利用部門」も書く |
| JSON・保存データの項目・件数が変わった | 12. データベース設計（件数は `45（コード進行の数）` のように数えた単位を括弧で残す）・13. コード設計（1件を一意に決める値は 13.1、処理の結果・エラーの値や通知文は 13.2 の正常／異常の表、それ以外の値は 13.3） |
| 見た目・内部の整理だけ | 直さない（報告の「直さなかった変更」に入れる） |

迷ったら、利用者から見た操作・結果が変わるかで決める。変わらなければ「直さない」。

## 3. 仕様書.md を直す

`基本設計書の作成手順.md` の「5-2」の形を崩さない（崩すと docx が作れなくなる）。とくに次を守る。

- 機能IDは変えない。機能が増えたらグループの最後の番号の次を使い、消えた機能の番号は使い回さない。新しいグループが要るときは新しいグループIDを作る。
- 新しい機能は 5.1 の表（`機能ID | 機能名 | 画面 | 説明`。「状況」の列は置かない）に行を足し、5.2 に `#### <機能ID> <機能名>機能` の節と「項目 | 内容」の表（`事前条件` `事後条件` `入力` `出力` `機能説明` `備考` の6行）を足す。入力・出力は `画面：…／データベース：…` のように区分で区切る。
- 未実装の機能を足すときは、5.2 の見出しの最後に「（未実装）」、備考に「未実装」と書く。
- **未実装だった機能が実装された**ときは、5.2 の見出しの「（未実装）」と備考の「未実装」を外して中身を実装に合わせ、6章・7章の前置きの文、付録B の未決事項の「未実装の機能」も直す。あわせて `docs/基本設計書/tools/build_docx.py` の `FIG_INTRO` と6章の置き換えの文にも未実装の機能が書かれているので、**直す必要があることを報告に書く**（スクリプトは `build-design-doc` スキルで直す）。
- 機能が消えたときは 5.1 の行と 5.2 の節を消し、付録C に消した機能IDと日付を書く（機能IDは欠番にして使い回さない）。
- 名前（画面・処理・データ）が増えたら付録A 名前の対応表に足す。図ではこの表の名前を使う。
- 機能ID・機能名・画面名を書く表記は、すでにある行に合わせる。
- **6.2 ユースケース記述も直す**（文章なのでこのスキルで書く。書き方は手順書の「2-1」）。
  - 機能が増えた（未実装を除く）・未実装だった機能が実装された：6.2 の、その機能のグループの節（なければグループの節も作る）に `##### <機能ID> <機能名>機能` の節と15行の表を足す。版数 `1`、作成日は今日、作者は前の記述に合わせる（分からなければユーザーに聞く）。
  - 動き・事前条件・事後条件・画面の操作が変わった：その機能の記述を 5.2 に合わせて直し、版数を1つ上げ、作成日を今日にする。
  - 機能名が変わった：5.2 と同じ見出しにし、ユースケース名も直す（版数を上げる）。
  - 機能が消えた：6.2 の節を消す（グループの機能がなくなればグループの節も消す）。
- **6.2 は推測で書かない。順番は「コード → 5.2 → 6.2」**（5.2 をいつも元にするため）。足す・直す記述ごとに次を行う。
  1. フローの分かれ道を `origin/main`（引数のコミット）のコードで確かめる。その機能の画面のボタンの処理（`src/ui/*.ts`）を読み、とくに次を探す：確認ダイアログ（`confirm(`）と取り消したときの動き、押せなくなる条件（`disabled`）、失敗・空のときの通知（`alert(`・メッセージ）、再生中かどうかで変わる動き、もう一度押したときの動き。
     ```
     git grep -n "confirm(\|alert(\|disabled" origin/main -- src/ui/<画面>.ts
     ```
  2. 確かめた動きのうち 5.2 に書いていないものは、先に 5.2 の「機能説明」（細かい補足は「備考」）に足す。
  3. 6.2 は 5.2 に書いてあることだけで書く。5.2 にない分かれ道は 6.2 に書かない。
  4. コードを読んでも分からない動き（ブラウザの動き・実行してみないと分からない順番など）は書かず、報告の「要確認」に挙げる（ユーザーがアプリを動かして確かめる。とくに例外フロー）。
- 6.1・7章の図へのリンク（`![…](図/…svg)`）はここでは足さない・消さない（`update-diagrams` で行う）。

## 4. 記録を更新する

1. 先頭の基準のコードの行を `main` のコミット `<HEAD>`（<今日の日付>「<HEAD のコミットの件名>」）に書き換える。
2. 付録C 更新履歴に1行足す。「図への反映」の列は、図の更新が必要な機能IDがあれば `要：B01-1・C01-7`（全体のクラス図・ユースケース図が要るときは `全体_クラス図` `C01_ユースケース図` のように書く）、なければ `不要`。
3. `基本設計書の作成手順.md` の「進み具合」の表の「2. 仕様書を作る」「4. コードが更新されたとき」の行に、日付と基準のコミットを書く。
4. `基本設計書の作成手順.md` の「6. まだ決まっていないこと」を、仕様書.md の付録B 未決事項とそろえる。今回の変更で解決したもの（例：未実装だった機能が実装された）は表から消して、表の下に「（○○は、△△ので解決した（日付）。）」と1行残す。新しく決めることが出てきたもの（例：テスト中の機能を設計書に載せるか）は、両方の表に足す。
5. `基本設計書の作成手順.md` の本文にある、仕様書の中身を写した数・一覧を今の仕様書.md に合わせる。とくに「1. 機能IDを決める」の「（○○機能。未実装の機能は …）」（5.1 の行数と、5.2 の見出しに「（未実装）」がある機能）と、「進み具合」の表の機能数・図の枚数。ほかにも機能数・未実装の機能名・件数を書いた文があれば `grep -n "機能。\|未実装\|[0-9]機能" docs/基本設計書/基本設計書の作成手順.md` で探して直す。過去の記録（「○○した（日付）」のように日付付きで書いた経緯）は、その時点の事実なので直さない。

## 5. 確かめる

- 5.1 の機能IDと 5.2 の節が1対1で対応しているか（`grep -n "^#### [A-Z][0-9][0-9]-"` と表の行を比べる）。
- 5.2 の節（「（未実装）」を除く）と 6.2 の `##### <機能ID> …` の節が、同じ見出しで1対1に対応しているか（`grep "^##### [A-Z][0-9][0-9]-"` と比べる）。6.2 の表がどれも15行そろっているか。
- 見出しの階層・表の行の名前が「5-2」の形のままか。
- 文書の中に「未実装」と書いた機能が、5.2 の見出しに「（未実装）」がある機能と一致しているか。
- 仕様書.md の付録B と、手順書の「6. まだ決まっていないこと」の項目がそろっているか。
- 手順書の「1. 機能IDを決める」の機能数・未実装の機能が、5.1 の行数・5.2 の「（未実装）」の機能と一致しているか。

## 6. 報告（毎回この形）

```
## 仕様書.md の更新
- 調べた範囲：<BASE>..<HEAD>（コミット N 件）
- 直したところ：章ごとに箇条書き（6.2 ユースケース記述は、足した・直した（版数）・消した機能ID）
- 6.2 のためにコードで確かめて 5.2 に足した動き：<機能ID と内容>
- 要確認（コードで確かめられず 6.2 に書かなかった動き）：<機能ID と内容／なし>
- 直さなかった変更：ファイル・コミットと理由（見た目だけ など）
- 図の更新が必要な機能：<機能ID の一覧>（→ `/update-diagrams` で更新）
- build_docx.py で直す必要があること：<あれば>
```

最後に、CLAUDE.md の決まりどおりコミットメッセージ案（`docs:` で始める）を示す。
