# 週報（担当者ごとの先週の作業・所感・今週の予定）

ガントチャートだけをもとに週報を作る。ガントチャートに書き込むのは先週のタスクの進捗（D 列）だけ。コード・仕様書は変えない。コミット・push はしない。

## 0. 前提（必ず守る）

- **日付は必ず実際の日付を確かめる。** 会話の中で思い込んでいる日付は使わない。最初に PowerShell で `Get-Date -Format "yyyy-MM-dd (ddd)"` を実行し、その日を基準の日にする。引数で日付が渡されたら、その日を基準にする。
- 週は**月曜〜日曜**。「先週」は基準の日の前の週の月曜〜日曜、「今週」は基準の日を含む週の月曜〜日曜（例：基準の日が 2026-11-24（火）なら、先週は 11/16〜11/22、今週は 11/23〜11/29）。
- **材料はガントチャートだけ。** Git のコミット・仕様書・コードは見ない。ガントチャートにないこと（作業・出来事・気持ちの理由）を作らない。
- 担当者は `根井`・`西薗`・`小手川` の3人（`gantt_check.py` の `MEMBERS`）。担当者が「全員」の行は3人ともに入れる。
- 手順の説明（メンバー向け）は `docs/基本設計書/週報の作成の進め方.md`。同じ週に `update-gantt` も行うときは、そちらを先に行う（`update-gantt` が開始・終了を割り当て直すと、書き込んだ進捗が違う期間の行に残るため）。
- ガントチャートの書き込みは、`update-gantt` スキルと同じく必ず `docs/基本設計書/tools/gantt_apply.ps1`（Excel に操作させる）で行う。xlsx を直接書き換えない・openpyxl で保存しない。シート「2027」は触らない。

## 1. 先週の進捗を 100% にする

リポジトリのルートで、PowerShell から実行する（作業用のファイルはスクラッチパッドに置く）。

```
[Console]::OutputEncoding = [Text.Encoding]::UTF8; py docs/基本設計書/tools/weekly_tasks.py --date <基準の日> --plan <作業用フォルダ>/progress.json
```

- `[進捗を 100% にする]` に出る行が対象：**先週にかかり、先週の日曜までに終わる予定で、進捗が 100% でない行**。終わりが今週以降のタスク（先週から続いているもの）はまだ途中なので変えない。
- `[要確認]`（先週より前に終わる予定なのに 100% でない行）は自動では変えない。報告の最後に知らせる。
- 対象が 0 行なら、2. へ進む（書き込み・番号の繰り上げはしない）。

対象があれば、`update-gantt` と同じ手順で当てる。

1. 元の xlsx を作業用フォルダに写して控える。
2. 写しで試す：`powershell -ExecutionPolicy Bypass -File "docs/基本設計書/tools/gantt_apply.ps1" -Plan <progress.json> -Out <作業用フォルダ>/test.xlsx`。そのあと `weekly_tasks.py --date <基準の日> --xlsx <test.xlsx>` で `[進捗を 100% にする]` が 0 行になったのを確かめる。
3. `-Out` を外して本物に当てる。「Excel で開かれています」で止まったら、ユーザーに Excel を閉じてもらってからやり直す（同じ計画を2回当てない）。
4. ファイル名の番号を1つ上げる：`powershell -ExecutionPolicy Bypass -File "docs/基本設計書/tools/gantt_bump.ps1"`（1回の更新につき1回）。
5. `[Console]::OutputEncoding = [Text.Encoding]::UTF8; py docs/基本設計書/tools/gantt_check.py` を当てる前と後で実行し、指摘（`[要…]`）が増えていないか確かめる（進捗しか変えないので増えないはず。当てる前からある指摘は `update-gantt` で直すものなので、ここでは直さずに報告で知らせる）。

## 2. 材料を集める

更新したあとのガントチャートで、もう一度実行する。

```
[Console]::OutputEncoding = [Text.Encoding]::UTF8; py docs/基本設計書/tools/weekly_tasks.py --date <基準の日>
```

担当者ごとに、先週にかかるタスク・今週にかかるタスク（節・行番号・期間・進捗）、今週のうちに終わる予定の件数、今週より後に始まるタスクが出る。

## 3. 書く

担当者ごとに、次の3つの見出しを順に書く。**どの見出しも箇条書きは1行だけ**にする（2行以上並べない）。その週に一番伝えたいことを1つ厳選し、40〜80字くらいの1文で書く。行の頭は「・」。文体は「〜した」「〜する」の常体（週報として提出できる書き方）。

- **列挙しない。** タスク・件数・期間を並べるのではなく、候補の中から1つを選ぶ。選び方の目安は「件数・期間が一番大きい作業」「次の作業に一番つながること」「一番気を付けること」。
- 1行に収めるために、「〜し、〜し、〜した」と複数の事柄をつなげて実質的に列挙しない。似たタスクをまとめて1つの作業として書くのはよい（例：「8ジャンルの音作り」）。
- ガントチャートにない作業・出来事・気持ちの理由は書かない。

### 先週の主な作業内容

- 先週にかかるタスク（1. で 100% にしたものを含む）のうち、主な作業1つを期間つきで書く（例：「7.音作りでテクノ・EDM など8ジャンルの音作りを行い、すべて終えた（11/16〜11/20）。」）。
- 先週から今週へ続いているタスクを選んだときは、「〜を進めた（11/30 まで）」のように途中として書く。

### 先週の所感・問題点

ガントチャートから読み取れることのうち、一番目立つ点を1つ書く。候補はたとえば次のようなもの。

- 先週のタスクの量・期間（同じ期間に重なっていた件数、期間の短いタスク）
- 1. で 100% にしたタスク・`[要確認]` の行（予定どおり進んでいるか、記録が遅れていないか）
- 今週の作業量（今週のタスクの件数・担当者の間の偏り）
- タスクのつながり（先週の成果を今週どこで使うか）

`[要確認]` の行がその人のタスクなら、それを優先して選ぶ。「所感」はその人の立場の一文にしてよい（「〜を早めに確かめておく」など）。

### 今週の主な作業内容予定

- 今週にかかるタスクのうち、主な作業1つを期間つきで書く。同じ期間・同じ節のものはまとめてよい（例：「8-01〜8-05.BPM・テンポ・小節数の選択機能をプログラミングし、11/27 までに終える。」）。
- `[要確認]` の行がその人のタスクなら、それを片付けることを選ぶ。
- 今週のタスクがないときは、今週より後に始まるタスクとその準備を書く。

## 4. 示す・保存する

- 会話に、最初に基準の日・先週・今週の期間・使ったガントチャートのファイル名、続けて担当者ごとの3つの見出しをそのまま示す（コピーして使えるように）。
- 同じ内容を `output/weekly/週報_<今週の月曜 YYYY-MM-DD>.md` にも保存する（`output/` は Git 管理外。同じ名前のファイルがあれば中身を見てから上書きする）。保存した場所を伝える。
- 最後に、進捗を 100% にした行（行番号・タスク名・担当者）、新しいファイル名、`[要確認]` の行を知らせる。100% にしたタスクが実際には終わっていない場合は、ガントチャートの進捗を戻すようユーザーに伝える。
