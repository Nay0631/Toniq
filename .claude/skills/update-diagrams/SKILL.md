# 図の作成・更新

図は**仕様書.md から描く**（コードから直接描かない）。毎回この手順どおりに行う。
最初に `docs/基本設計書/図/CLAUDE.md`（図の書き方の決まり）と `docs/基本設計書/基本設計書の作成手順.md` の「3. 図を作る」を読む。

## 0. 前提の確認（ここで止まることがある）

1. `java -version` が動くか確かめる（PowerShell で `Get-Command java`）。なければ**作業を始めずに止め**、ユーザーに Java のインストール（例 `winget install EclipseAdoptium.Temurin.21.JRE`）を頼む。ロバストネス図・ER図を作る・直すときは `node` も要る（`Get-Command node`。なければ `winget install OpenJS.NodeJS.LTS` を頼む）。
2. `tools/plantuml.jar` があるか確かめる。
3. 仕様書.md の基準のコードが `origin/main` より古くないか確かめる（`git fetch origin` のあと、基準のコミットと `git rev-parse --short origin/main` を比べる）。古ければ「先に `/update-spec` で仕様書を更新したほうがよい」とユーザーに伝え、続けるかどうかを聞く。
4. コミット・push はしない。

## 1. 作る・直す図を決める

基本設計書の図は次の表の6種類で全部（画面のスクリーンショットは図ではないのでここでは扱わない）。

| 図の種類（引数） | ファイル | もとにする仕様書の節 | 仕様書のリンクの場所 |
|---|---|---|---|
| ユースケース図 | `図/ユースケース図/<グループID>_<システム名>_ユースケース図.puml`（グループごと） | 5.1 機能一覧 | 6.1 |
| 機能の図（ロバストネス図・シーケンス図・クラス図） | `図/ロバストネス図/`・`図/シーケンス図/`・`図/クラス図/` の `<機能ID>_<機能名>機能_<図の種類>.puml`（機能ごとに3枚） | 5.2 機能・付録A 名前の対応表 | 7章 |
| 画面遷移図 | `図/画面遷移図/全体_画面遷移図.puml` | 10.1 画面一覧・10.2 遷移の条件 | 10.2 |
| システム概要図 | `図/システム図/システム概要図.puml` | 3.1・3.2・付録A | 3.3 |
| システム構成図 | `図/システム図/システム構成図.puml` | 4.2 システム構成表 | 4.1 |
| ER図 | `図/ER図/ER図.puml` | 12.1 テーブル定義・12.2 の関係 | 12.2 |

引数で作る図を決める（スペース区切りで混ぜてよい。例 `B01-1 ER図`）。

- `all`：上の表の**すべての図**を作り直す。実装済みのすべての機能の機能の図、すべてのグループのユースケース図、画面遷移図、システム概要図、システム構成図、ER図（全体のユースケース図・全体のクラス図は作らない。2026-11-16 決定）。1種類も飛ばさない。
- 機能ID（`B01-1` など）：その機能の機能の図3枚（と、必要ならその機能のグループのユースケース図）。
- 図の種類の名前：その種類の図をすべて作り直す。`ユースケース図`＝全グループのユースケース図、`機能の図`＝全機能の3枚ずつ、`システム図`＝システム概要図とシステム構成図、ほかは1枚。
- 引数なし：仕様書.md の付録C 更新履歴の「図への反映」が `要：…` の行に書かれたもの（機能ID、`C01_ユースケース図`、`画面遷移図`、`システム概要図`、`システム構成図`、`ER図` など）。`要` の行がなければ「更新が必要な図はない」と報告して終わる。

システムの開発のためのテスト・確認に作ったもの（テスト中の機能切替・自動チェック・メロディの評価など。仕様書.md に載せないもの。`update-spec` の「載せないもの」）の図は作らない。ユースケース図・画面遷移図にも入れない（2026-11-19 決定）。

作り直す図は、今の .puml を開いて仕様書の該当の節と見比べ、違う所を直す（同じなら変えなくてよいが、`all` や図の種類を指定されたときも SVG への変換と後処理はやり直す）。機能ID・`要` の行から決めるときは、次のどれに当たるかを決める。

| 場合 | すること |
|---|---|
| 新しい機能（実装済み） | ロバストネス図・シーケンス図・クラス図を新しく作る。グループのユースケース図に足す |
| 未実装 → 実装済み | 同上（6章・7章の「未実装の … は図に含めない」の文も直す） |
| 動きが変わった | その機能の3つの図を仕様書の機能定義に合わせて直す |
| 機能名が変わった | 図のファイル（.puml / .svg）の名前と枠の図名を変え、古いファイルを消す |
| 廃止 | その機能の図のファイルを消し、ユースケース図から外す（消したファイルは報告に書く） |
| 画面が増えた・減った・遷移が変わった（仕様書の 10.1 画面一覧・10.2 遷移の条件が変わった。`all` のときも） | `図/画面遷移図/全体_画面遷移図.puml` を 10.1・10.2 に合わせて直す |
| 3.1・3.2 の画面・処理の流れ、4.2 システム構成表が変わった（`all` のときも見直す） | `図/システム図/システム概要図.puml`（3.1・3.2）・`システム構成図.puml`（4.2。部品の図番号 ①②… を構成表の行と1対1に）を直す |
| 12.1 テーブル定義・12.2 の関係が変わった（テーブル・項目・主キー・参照が増えた・減った。`all` のときも見直す） | `図/ER図/ER図.puml` を 12.1・12.2 に合わせて直す（IDEF1X の記法。`図/CLAUDE.md` の「ER図」） |

## 2. .puml を書く

- `図/CLAUDE.md` の決まりにすべて従う（ファイル名、`!include` する共通設定、`mainframe`、日本語の名前、矢印の向き、つないでよい組み合わせ、`{method} <U+002B> 操作名() : void` など）。
- 名前は仕様書の付録A 名前の対応表の名前を使う。表にない名前が要るときは、先に付録A に足す。
- 書き方は、同じ種類のすでにある図（例 `図/ロバストネス図/B01-1_BPM選択機能_ロバストネス図.puml`）を開いて形をそろえる。
- 細かさは利用者の操作の単位。画面の描き直し・状態の読み書きは書かない。
- シーケンス図のメッセージとクラス図の矢印の向きをそろえる。

## 3. SVG に変換して確かめる

リポジトリのルートで、変えた .puml だけを変換する（全部のときは `"docs/基本設計書/図/**/*.puml"`）。

```
java -jar tools/plantuml.jar -tsvg -charset UTF-8 "<変えた .puml のパス>" "<…>"
```

- 変換した .svg に「Syntax Error」が含まれていないか、`grep -l "Syntax Error"` で確かめる。あれば直して変換し直す。
- ロバストネス図を変換したら、**必ず**続けて線の文を置き直す（矢印のすぐ上に、矢印と平行に置く。処理済みの SVG は変えないので、いつも引数なしで全部に当ててよい）：
  ```
  node docs/基本設計書/tools/robustness_labels.mjs
  ```
  「重なり N 件」と出た図は、`図/CLAUDE.md` の決まり（ラベルを短くする・13文字くらいで `\n` で改行、自己ループは1つの処理に1本まで、処理の手順は別の処理に分ける）に合わせて .puml を直し、変換からやり直す。置き直した SVG は手で直さない。
- ロバストネス図は、文字（線のラベル・名前）どうし・文字と線が重なっていないか画像で確かめる。PNG は `node docs/基本設計書/tools/robustness_labels.mjs <変えた SVG …> --png <スクラッチパッドのフォルダ>` で作る（Edge か Chrome で描く。PlantUML の `-tpng` は置き直す前の配置になるので使わない）。
- ER図を変換したら、**必ず**続けて名前を箱の上に出し、子の側の丸を黒丸にする（処理済みの SVG は変えないので、いつも引数なしでよい）。書き換えた SVG は手で直さない：
  ```
  node docs/基本設計書/tools/er_layout.mjs
  ```
  画像で確かめるときは `node docs/基本設計書/tools/er_layout.mjs --png <スクラッチパッドのフォルダ>` で PNG を作る（PlantUML の `-tpng` は書き換える前の見た目になるので使わない）。
- 全部（`**/*.puml`）を変換したときは、ロバストネス図・ER図の両方のスクリプトを動かす（変換し直した SVG は印が消えているため）。
- 共通設定ファイル（`astah-*.puml`）の「no image」の警告は問題ない。
- .puml があって .svg がない（または逆の）ファイルが残っていないか、フォルダごとに確かめる。
- `all` のときは、1 の表の6種類すべての .svg が今回の変換で新しくなったか（更新日時）を確かめ、抜けた種類があれば変換し直す。ロバストネス図・ER図は、後処理の印（`<!--robustness-labels-->`・`<!--er-layout-->`）が SVG に入っているかも確かめる。

## 4. 仕様書.md に図へのリンクを書く

画像のデータは入れず、SVG ファイルの場所を指すリンクだけを書く（図を実際に貼り付けるのは docx を作るとき）。


- 6.1（ユースケース図）は `#### <グループID>_<システム名>`（全体の節は置かない。見出しに「_ユースケース図」は付けない）の節に `![<図名>](図/ユースケース図/<図名>.svg)`（図名は `<グループID>_<システム名>_ユースケース図`）。6.2 ユースケース記述は文章なのでここでは直さない（`/update-spec` で直す）。ユースケース図に足した・外した機能と、6.2 の記述の機能がずれていたら報告に書く。
- 7章はシステムごとに `### <グループID>_<システム名>` の節を置き、その中に機能IDの順に `#### <機能ID>_<機能名>機能` の節を置いて、次の3行（空行で区切る）を書く。システム名は仕様書 5.1 の表の1行目の名前。alt は図の種類（docx を作るときに使う）。
  ```
  ![ロバストネス図](図/ロバストネス図/<機能ID>_<機能名>機能_ロバストネス図.svg)

  ![シーケンス図](図/シーケンス図/<機能ID>_<機能名>機能_シーケンス図.svg)

  ![クラス図](図/クラス図/<機能ID>_<機能名>機能_クラス図.svg)
  ```
- 3.3 システム概要図は `![システム概要図](図/システム図/システム概要図.svg)`、4.1 システム構成図は `![システム構成図](図/システム図/システム構成図.svg)`。
- 12.2 ER図は `![ER図](図/ER図/ER図.svg)`（その下の記法の説明と関係の箇条書きは残す）。
- 10.2 画面遷移図は、節の先頭に `![全体_画面遷移図](図/画面遷移図/全体_画面遷移図.svg)`（その下の「遷移の条件」の箇条書きは残す）。
- 消した図へのリンクは消す。仕様書の中の `.svg` へのリンクがすべて実在するか確かめる。`all` のときは、1 の表の「仕様書のリンクの場所」のすべてにリンクがあるか（「（図は未作成）」のような文が残っていないか）も確かめる。

## 5. 記録を更新する

1. 付録C の、今回反映した行の「図への反映」を `済（<今日の日付>）` にする（一部だけなら残りを `要：…` のまま残す）。
2. `基本設計書の作成手順.md` の「進み具合」の「3. 図を作る」の行に日付と枚数を書く。

## 6. 報告（毎回この形）

```
## 図の更新
- 対象：<機能ID・図の種類の一覧／all>
- 図の種類ごとの枚数：ユースケース図 N 枚／機能の図 N 機能（N 枚）／画面遷移図 1 枚／システム概要図 1 枚／システム構成図 1 枚／ER図 1 枚（対象外の種類は「対象外」）
- 作った図：<ファイル名>
- 直した図：<ファイル名と直したところ>
- 消した図：<ファイル名>
- Syntax Error：なし
- 残っている「要」：<あれば>
```

最後に、CLAUDE.md の決まりどおりコミットメッセージ案（`docs:` で始める）を示し、続けてプルリクエストの説明文案（見出しは「概要」「変更内容」「動作確認」「補足」。動作確認には Syntax Error の有無・リンクの確認の結果と、図を開いて見た目を確かめることのチェックリストを書く）を示す。どちらも省かない。
