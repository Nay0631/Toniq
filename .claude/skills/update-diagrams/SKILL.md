# 図の作成・更新

図は**仕様書.md から描く**（コードから直接描かない）。毎回この手順どおりに行う。
最初に `docs/基本設計書/図/CLAUDE.md`（図の書き方の決まり）と `docs/基本設計書/基本設計書の作成手順.md` の「3. 図を作る」を読む。

## 0. 前提の確認（ここで止まることがある）

1. `java -version` が動くか確かめる（PowerShell で `Get-Command java`）。なければ**作業を始めずに止め**、ユーザーに Java のインストール（例 `winget install EclipseAdoptium.Temurin.21.JRE`）を頼む。
2. `tools/plantuml.jar` があるか確かめる。
3. 仕様書.md の基準のコードが `origin/main` より古くないか確かめる（`git fetch origin` のあと、基準のコミットと `git rev-parse --short origin/main` を比べる）。古ければ「先に `/update-spec` で仕様書を更新したほうがよい」とユーザーに伝え、続けるかどうかを聞く。
4. コミット・push はしない。

## 1. 作る・直す図を決める

- 引数が `all`：実装済みのすべての機能の図と、全体・グループのユースケース図、全体のクラス図を作り直す。
- 引数が機能ID：その機能の図（と、必要ならその機能のグループのユースケース図・全体のクラス図）。
- 引数なし：仕様書.md の付録C 更新履歴の「図への反映」が `要：…` の行に書かれたもの。`要` の行がなければ「更新が必要な図はない」と報告して終わる。

機能ごとに、次のどれに当たるかを決める。

| 場合 | すること |
|---|---|
| 新しい機能（実装済み） | ロバストネス図・シーケンス図・クラス図を新しく作る。グループのユースケース図と全体のユースケース図に足す。全体のクラス図に新しいクラスがあれば足す |
| 未実装 → 実装済み | 同上（6章・7章の「未実装の … は図に含めない」の文も直す） |
| 動きが変わった | その機能の3つの図を仕様書の機能定義に合わせて直す |
| 機能名が変わった | 図のファイル（.puml / .svg）の名前と枠の図名を変え、古いファイルを消す |
| 廃止 | その機能の図のファイルを消し、ユースケース図から外す（消したファイルは報告に書く） |
| 画面が増えた・減った・遷移が変わった（仕様書の 10.1 画面一覧・10.2 遷移の条件が変わった。`all` のときも） | `図/画面遷移図/全体_画面遷移図.puml` を 10.1・10.2 に合わせて直す |

## 2. .puml を書く

- `図/CLAUDE.md` の決まりにすべて従う（ファイル名、`!include` する共通設定、`mainframe`、日本語の名前、矢印の向き、つないでよい組み合わせ、`{method} <U+002B> 操作名() : void` など）。
- 名前は仕様書の付録A 名前の対応表の名前を使う。表にない名前が要るときは、先に付録A に足す。
- 書き方は、同じ種類のすでにある図（例 `図/ロバストネス図/B01-1_BPM選択機能_ロバストネス図.puml`）を開いて形をそろえる。
- 細かさは利用者の操作の単位。画面の描き直し・状態の読み書きは書かない。
- シーケンス図のメッセージとクラス図の矢印の向きをそろえる。

## 3. SVG に変換して確かめる

リポジトリのルートで、変えた .puml だけを変換する（全部のときは `"docs/基本設計書/図/**/*.puml"`）。

```
java -jar tools/plantuml.jar -tsvg -charset UTF-8 "<変えた .puml のパス>" "<…>"
```

- 変換した .svg に「Syntax Error」が含まれていないか、`grep -l "Syntax Error"` で確かめる。あれば直して変換し直す。
- ロバストネス図は、文字（線のラベル・名前）どうしが重なっていないか確かめる（PNG にして画像で見るか、SVG の `<text>` の位置と幅を比べる）。重なっていたら `図/CLAUDE.md` の自己ループの決まり（1つの処理に1本まで、13文字くらいで `\n` で改行、処理の手順は別の処理に分ける）に合わせて直す。
- 共通設定ファイル（`astah-*.puml`）の「no image」の警告は問題ない。
- .puml があって .svg がない（または逆の）ファイルが残っていないか、フォルダごとに確かめる。

## 4. 仕様書.md に図へのリンクを書く

画像のデータは入れず、SVG ファイルの場所を指すリンクだけを書く（図を実際に貼り付けるのは docx を作るとき）。


- 6.1（ユースケース図）は `#### <グループID>_<システム名>`（全体は `#### 全体_楽曲生成システムToniq`。見出しに「_ユースケース図」は付けない）の節に `![<図名>](図/ユースケース図/<図名>.svg)`（図名は `<グループID>_<システム名>_ユースケース図`）。6.2 ユースケース記述は文章なのでここでは直さない（`/update-spec` で直す）。ユースケース図に足した・外した機能と、6.2 の記述の機能がずれていたら報告に書く。
- 7章はシステムごとに `### <グループID>_<システム名>` の節を置き、その中に機能IDの順に `#### <機能ID>_<機能名>機能` の節を置いて、次の3行（空行で区切る）を書く。システム名は仕様書 5.1 の表の1行目の名前。alt は図の種類（docx を作るときに使う）。
  ```
  ![ロバストネス図](図/ロバストネス図/<機能ID>_<機能名>機能_ロバストネス図.svg)

  ![シーケンス図](図/シーケンス図/<機能ID>_<機能名>機能_シーケンス図.svg)

  ![クラス図](図/クラス図/<機能ID>_<機能名>機能_クラス図.svg)
  ```
- 10.2 画面遷移図は、節の先頭に `![全体_画面遷移図](図/画面遷移図/全体_画面遷移図.svg)`（その下の「遷移の条件」の箇条書きは残す）。
- 消した図へのリンクは消す。仕様書の中の `.svg` へのリンクがすべて実在するか確かめる。

## 5. 記録を更新する

1. 付録C の、今回反映した行の「図への反映」を `済（<今日の日付>）` にする（一部だけなら残りを `要：…` のまま残す）。
2. `基本設計書の作成手順.md` の「進み具合」の「3. 図を作る」の行に日付と枚数を書く。

## 6. 報告（毎回この形）

```
## 図の更新
- 対象：<機能ID の一覧／all>
- 作った図：<ファイル名>
- 直した図：<ファイル名と直したところ>
- 消した図：<ファイル名>
- Syntax Error：なし
- 残っている「要」：<あれば>
```

最後に、CLAUDE.md の決まりどおりコミットメッセージ案（`docs:` で始める）を示す。
