# 仕様書.md から基本設計書（docx）を作る

docx は**直接直さず**、仕様書.md と図から作り直す。毎回この手順どおりに行う。
詳しい決まりは `docs/基本設計書/基本設計書の作成手順.md` の「5. docx を作る」にある（スクリプトが止まったときだけ読めばよい）。
コミット・push はしない。確認のためのスクリプトをその場で書かない（下の2つのスクリプトの結果だけで判断する）。

## 1. 事前の確認（preflight.py）

リポジトリのルートで、PowerShell から1回だけ実行する。

```
[Console]::OutputEncoding = [Text.Encoding]::UTF8; py docs/基本設計書/tools/preflight.py
```

必要なもの・出力先の docx が閉じているか・仕様書の基準と origin/main（`git fetch` 込み）・付録C の「要：」・5.2 と 6.2 の対応・未実装の機能と `build_docx.py` の文を `[OK]` / `[NG]` で出し、次の版数と改訂の概要の材料（前回より後の付録C の行）も出す。

`[NG]` があれば、スクリプトを動かす前に止めて、その行のとおりにする。

| NG の行 | すること |
|---|---|
| 必要なもの | 足りないものと入れ方（行に書いてある）をユーザーに伝えて止める |
| 出力先の docx | ユーザーに Word で閉じてもらう |
| 仕様書の基準と origin/main（コードの変更あり） | 先に `/update-spec` を行うか、このまま作るかを聞く（docs だけの差は OK になる） |
| 付録C の「要：」 | 先に `/update-diagrams` を行うか、このまま作るかを聞く |
| 5.2 と 6.2 | 先に `/update-spec` で記述を直すか、このまま作るかを聞く（6.2 の表の行が足りないと `build_docx.py` が止まる） |
| 未実装の機能 | `build_docx.py` の `FIG_INTRO` と6章の置き換えの文を仕様書に合わせて直す（未実装がなくなったら「未実装の … は」の文ごと外し、未実装の機能ができたら「未実装の ○○ は実装後に作成する。」の文を足す）。直したことは報告に書く |

## 2. 版数と改訂の概要を決める

- 版数（`-Rev`）：引数があればそれ。なければ preflight の「次の版数」。2桁で書く。
- 改訂の概要（`-RevNote`）：引数があればそれ。なければ `仕様書.md（基準：main <基準のコミット>）の内容で改訂。` に続けて、preflight が出した付録C の行の内容を1文に縮めて書く（タブは使わない）。
- 決めた版数と改訂の概要は、スクリプトを動かす前にユーザーに示す（違っていれば直してもらう）。

## 3. スクリプトを動かす

PowerShell からタイムアウトを長め（10分）にして実行する。

```
powershell -ExecutionPolicy Bypass -File "docs/基本設計書/tools/build_docx.ps1" -Rev <版数> -RevNote "<改訂の概要>"
```

- PNG は図（`.puml`）が変わったときだけ自動で作り直す（`-SkipPng` / `-ForcePng` はふつう要らない）。
- ロバストネス図は、スクリプトが線の文を矢印のすぐ上・平行に置き直し（`robustness_labels.mjs`。処理済みなら何もしない）、PNG も置き直した SVG から作る。「重なり」と出たら報告に書く（docx は作られる）。
- 改訂履歴は `tools/改訂履歴.tsv` に今回の版が足され（同じ版なら上書き）、01 の下に全部並ぶ。表紙の文書番号の「(01)」は版数になる。
- 最後に `check_docx.py` が表紙の文書番号・日付、改訂履歴、目次、機能定義・ユースケース記述の表の数、図の数を `[OK]` / `[NG]` で出す。これが docx の確認になる。**PDF は作らない**（Word の PDF 書き出しは戻ってこないことがある）。
- 「ページ数」を控え、preflight に出た前回のページ数と大きく違えば理由を考える（表や図の増減で説明できるか）。
- 止まったとき：
  - 「出力先の docx がほかのプログラムで開かれています」→ ユーザーに閉じてもらって再実行。
  - `assert` → 手本の docx が編集されて段落の番号がずれている（作成手順の「5-3」）。勝手に番号を直さず、ユーザーに知らせる。
  - `check_docx.py で NG` → `[NG]` の行を報告し、原因（仕様書・スクリプト）を確かめる。
  - 画面のない `WINWORD` が残ったら、止めずにユーザーにタスクマネージャーで終了してもらう（PID を伝える）。

## 4. 記録を更新する

`基本設計書の作成手順.md` の「進み具合」の「5. docx を作る」の行を、`版 <版数> を作成済（<今日の日付>、仕様書.md 基準 main <基準のコミット>、<ページ数>ページ）` に書き換える。

## 5. 報告（毎回この形）

```
## 基本設計書（docx）の作成
- 版数／改訂の概要：
- 基準のコード：main <コミット>
- ページ数：N（前回 M）
- build_docx.py で直したこと：<あれば>
- 確認（check_docx.py）：<[OK] / [NG] の結果を短く>
- 目で確かめてほしいこと：Word で開いて、表紙・改訂履歴・目次・表・図のページの見た目
```

docx は約18MB。リポジトリは公開されているので、push は提出版など区切りのときだけにするよう、報告で一言添える。`tools/改訂履歴.tsv` も一緒にコミットするよう伝える。最後に、CLAUDE.md の決まりどおりコミットメッセージ案（`docs:` で始める）を示す。
